# 模拟 MR 联调验收

这份记录区分模拟 GitLab 与真实协作链路：Git 仓库、分支、CI 状态和 MR 注册表在本机隔离模拟；MM 指令、HTTP 接收器、持久队列、Qoder 团队执行和结果通知实际运行。不连接真实 GitLab，不证明生产环境合并能力。

## 验收方式

通过 MM 创建模拟仓库、配置团队并实际克隆，通过 MM 配置 webhook 规则。模拟事件经本机 HTTP 接收器触发团队。团队完成后独立复跑测试并检查工作区未变化，再通过 MM 登记精确版本的核对结果、执行模拟合并，读取目标 Git 引用和文件内容确认结果。

每个场景保存 MM 命令及回复线程、任务 ID、MR 源/目标 SHA、独立验收和合并提交。运行证据位于本机忽略目录 `.runtime/goal-validation/mock-*.json`，不会将票据或运行缓存上传仓库。失败尝试保留；修复后显式重试产生关联任务，不能覆盖失败历史或将模型口头 PASS 计为成功。

| 场景 | 必须验证的行为 |
|---|---|
| 正常合并 | 真实团队核对、独立测试、精确 SHA 合并及目标内容一致 |
| CI 失败后恢复 | CI 失败时拒绝合并，目标引用不变；同版本 CI 恢复后重新核对并合并 |
| 评审后提交变化 | 陈旧核对结果不能批准新提交；新版本触发新任务并重新核对 |
| 冲突处理 | 检测出冲突，诊断不移动引用；夹具解决冲突后由团队核对最终版本 |
| 接收器重启与重复投递 | 仅重启接收线程；重复通知仍返回原任务；重复合并及合并后通知不产生新的任务或合并 |

冲突修复由测试夹具准备，本轮不声称 Agent 自主解决了真实业务冲突。团队遇到模拟语义歧义时，曾在 MM 提问并从检查点继续，保留评审退回和再次开发的记录。

## 已确认的边界

- 当前重复投递保证依赖持久化 delivery receipt；升级前未保存该记录的历史事件不自动获得该保证。
- 重启测试覆盖 HTTP 接收线程重启，不等于整机断电恢复或所有进程崩溃点测试。
- 接收器仅监听本机环回地址。真实 GitLab 还需要可达的 HTTPS 入口、仓库权限及真实平台适配和联调。
- 模拟 CI 状态由测试显式设置，不能作为真实 GitLab CI 成功的证据。
- `/ops mock check` 检查任务、版本和工作区证据；业务测试结果仍必须独立验收。
